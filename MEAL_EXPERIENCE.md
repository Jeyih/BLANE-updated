# Meal experience updates

Recipes has a Dessert filter using existing recipe names/ingredients. Dessert discovery does not change food identities, servings or nutrition in the database. Cards and recipe details offer a one-tap Use today action; it replaces only today's matching meal slot and preserves other meals, custom times and other days. Dietary conflicts disable the quick-add action.

The Dashboard uses Asia/Manila time and shows only remaining meal options: Breakfast disappears at 10:30 AM, Lunch at 1:00 PM, and Snack at 6:30 PM. Dinner stays available until midnight, when the next day's options return. Brunch follows the Lunch cutoff and Dessert follows Snack. These display cutoffs also apply to custom serving times; saved slots are preserved, and full-day totals still include all planned meals. If no remaining meals are planned, the Dashboard shows an explicit empty state. Recommendations advance to an available meal type and never fall back to expired Breakfast. The clock checks at each minute boundary and on focus/visibility changes, so the user does not need to log in again. Recommendations use deterministic ranking and exclude recipes flagged by profile constraints. Recipe links open the selected recipe directly. Saved-plan changes update the Dashboard immediately.

Consumer meal costs display Est. and a concise statement that store totals may vary. Official source-product prices in Admin retain their original source values. The existing Philippines-only automatic price feed continues: browser checks every 15 seconds, retailer cache 30 seconds, DA reports separately cached and manual force checks available in Admin. Unchanged price polls reuse existing records so recommendation cards do not reshuffle or reload merely because a price check ran.

Validation covers exact Philippine meal cutoffs, midnight rollover, custom times, missing upcoming slots, preservation of saved plans, one-tap plan persistence, dessert classification, dynamic price timing and source rules. All 33 tests passed; production build passed. Protected pages were not visually verified with an authenticated browser session.

## Responsive layout follow-up

Shared responsive CSS now loads after page styles. Dashboard meal headers wrap on narrow screens; phones place the food icon/calories above full-width meal text, recipe action and macro badges. Meal tabs use two columns on phones. Recommendation cards use one column on phones, two on narrower tablets and three on desktop. Recipe searches use full mobile width, touch controls have larger targets, and Markets ingredient prices stack without the previous fixed-column overflow. Fixed navigation offsets and scrollable mobile drawers match the 68px navbar.

A representative layout fixture using the same production styles was visually inspected and measured at 320, 375, 390, 430, 768, 1024 and 1440 pixels. None had horizontal overflow. The authenticated live pages were unavailable in the test browser session, so this was a layout-fixture check rather than a signed-in workflow test. The production build and whitespace check passed. ## Affordable suggestion resilience

The Price-Aware Meal Optimizer now defaults to affordable meals with complete sourced price estimates. Per-meal allocation uses the exact daily budget divided by four. Unverified or incomplete prices are available for inspection through View all meals; they are not treated as affordable. AI suggestions are repriced when the price feed changes.

Suggest a meal uses a bounded in-memory 15-minute cache keyed by user, profile, dietary definitions, budget and meal type. Concurrent identical requests share one call. Cached suggestions are checked against current prices and dietary rules before reuse. No health profiles are persisted by this cache; refreshing the page clears it. A quota response starts a browser-session cooldown using the provider's retry delay when available. Other failures use a 30-second cooldown; requests time out after 12 seconds. These are browser-side protections, not a project-wide server cache.

When generation fails or cannot provide a suitable meal, a deterministic fallback chooses the cheapest existing recipe of the requested type with complete sourced prices and no violations under the loaded dietary definitions. The UI explicitly labels this as an existing-recipe fallback. Missing dietary definitions or unmapped preferences fail closed; no suitable recipe produces a concise empty-result message. This requires loaded recipe data and available authentication/constraint data, and does not provide full offline operation. Portion optimization and Why explanations are separate features and are not changed by this suggestion cache.

All 41 tests and the production build passed. Tests cover quota cooldown, cache expiration and concurrent requests, user/budget separation, changed prices, fallback type/budget/dietary checks, and absence of a suitable fallback. Live Gemini quota behavior was simulated; no quota-consuming integration request was made.
